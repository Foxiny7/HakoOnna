## 2. 模块 T：箱女 / 箱人的普通转移重做

### T.0 为什么改

现在的实现：同房间的容器互通；相邻两个房间之间只连**一对**最近的容器（“出口箱”）。换房间要先跳到出口箱，再跳过去，到了下个房间再找它的出口箱。操作是先点选、再按 E 两步。

设计者的要求【已定，2026-11-22】：

1. **就近转移，一个房间一个房间地走。**
2. 不要出现“困在一个房间里找不到出路”。**一楼和二楼之间、主屋和外面那栋土蔵之间的转移尤其要顺手，不能麻烦。**
3. 选目标保留**三种视角**：箱内视角、视角转移（房间视角）、3D 地图。
4. **不做**“设目的地、画路线、按住 E 自动连跳”。每一跳都由玩家自己决定。
5. 转移冷却现在的 3 秒只是方便测试的值，设计者之后会改。所有设计都**不能依赖冷却是 3 秒**。

V1.2 第 2.4 条本来就写着普通转移“没有视线或距离方面的隐蔽条件，只受转移冷却限制”，“出口箱”这层限制规则里没有，去掉它不违反任何已确认规则。“普通转移的目标距离范围”在 V1.2 第 3 节是待定数值，这次落定为“本房间 + 相邻房间”。

### T.1 规则（服务器）

- **可达目标** = 当前容器所在房间里的其他容器 + 所有**相邻房间**里的全部容器。不再有“出口箱”。
- 其余照旧：每次转移后进入冷却（`transferCooldownSeconds`，测试值 3 秒）；每次转移必定产生滚动音效；不能进入正在被交互或打开的容器；容器正在被打开时里面的藏匿者仍可转移离开。
- 箱人用同一套规则（V1.2 第 2.7 条）。
- 服务器校验改成：`Routes.Allows(from, to)` = 同房间，或 `from` 的房间与 `to` 的房间相邻。`MatchRules.TryTransfer` 不用动。

### T.2 房间图

过渡期直接沿用 `HiderRoutes.neighbours` 这张表，只把“每对房间只连一对容器”的逻辑删掉。这一步不需要美术配合，可以马上做。之后由美术导出 `HouseGraph`（见 T.10）替换手写的表。

房间图里有三处**特殊连接**，是这次体验的重点：

| 连接 | 现在表里的边 | 类型 |
|---|---|---|
| 后楼梯 | 台所 Daidokoro ↔ 二楼物置 Monooki | 跨楼层 |
| 主楼梯 | 奥の間 Oku ↔ 二楼子供部屋 Kodomo | 跨楼层 |
| 后院 | 風呂 Furo ↔ 土蔵 Kura | 跨建筑 |

按现在的表，从一楼各房间出发要几跳（已用代码里的表算过）：

| 出发房间 | 到二楼 | 到土蔵 |
|---|---|---|
| 台所、奥の間 | 1 | 3 |
| 玄関、居間、納戸、座敷 | 2 | 2–4 |
| 次の間、仏間、縁側、便所、風呂 | 3 | 1–4 |
| 二楼最远的房间（寝室、二楼和室） | — | **5** |

土蔵现在只连着風呂一个房间，是一条死胡同：进出都只能走風呂，从玄関过去要 4 跳，从二楼过去要 5 跳。

**【已定，2026-11-22】给土蔵加一条边：台所 ↔ 土蔵（`HouseGraph` 里已经有了，共 27 条）。** 理由：房子里真正通往后院和土蔵的门就是台所的后门，这条边符合房子的实际走法。加了以后：

- 玄関到土蔵从 4 跳变 2 跳；二楼物置到土蔵 2 跳；全图到土蔵最多 4 跳（原来 5）。
- 土蔵有了两个出入口，不再是死胡同，箱女进去以后不会被一条路堵死。
- 要不要加由设计者定；不加的话下面的体验设计照样成立，只是去土蔵多绕两步。

### T.3 跨楼层和去土蔵：通道栏

问题：在箱内视角里，楼上的容器在头顶正上方，土蔵隔着整个后院只有很小的剪影，都不好瞄。所以这两类转移**不要求瞄准**，用一条常驻的“通道栏”来做。

**通道栏**在屏幕底部，一直显示。每个相邻房间一个格子，带数字键。下面是箱女在奥の間时的样子：

```
本房间 2 │ 1 座敷 4   2 納戸 3 ⌂ │ 3 ↑二楼 子供部屋 2
```

- 格子里的数字是那个房间现在**能进的容器数**（正被探索者交互的不算）。
- **普通相邻房间**在左边，绿色。
- **跨楼层 / 跨建筑的相邻房间**单独放在右边，蓝色，带图标：`↑` 上楼、`↓` 下楼、`⌂` 去土蔵、`↩` 从土蔵回主屋。
- **方向徽标**：如果当前房间没有直接通楼上（或楼下、土蔵）的连接，那么“往哪个相邻房间走能更近一步”的格子右上角会带一个小的 `↑` / `↓` / `⌂`。例：上面奥の間的通道栏里，“納戸”带着 `⌂`，意思是往納戸走离土蔵更近；在座敷时，“奥の間”的格子上会有 `↑`，意思是先去奥の間，到了那里就会出现“↑二楼”的蓝格子。
  - 徽标只是提示，不会自动走。它只针对“另一层楼”和“土蔵”这三个目的地，不是通用的寻路。
- **短按数字键**：镜头切到那个房间的房间视角（T.4 的视角转移），在那里对准容器按 E。
- **长按数字键**（`quickHopHoldSeconds`，占位 0.35 秒）：**直接转移**到那个房间里离自己最近的可进入容器。这是一次普通转移，服务器照常校验、冷却、出声。上楼、下楼、去土蔵都是一个键的事。
- 冷却中：整条通道栏变暗，上面走一条冷却进度；冷却结束有一声很轻的提示音（见音效方案的 `Transfer_Ready`）。因为冷却时长以后会改，进度条按实际冷却值画，不写死。
- 某个房间的容器全都进不去：格子变灰并显示“被占用”。

**重点用例**（实现后要逐条手动验一遍）：

| # | 情况 | 操作 | 按键次数 |
|---|---|---|---|
| A | 同房间换一个箱子 | 对准黄色剪影按 E | 1 |
| B | 去隔壁房间，看得见目标 | 对准绿色剪影按 E | 1 |
| C | 去隔壁房间，想先看看 | 短按数字键看那个房间 → 对准按 E | 2 |
| D | 在台所 / 奥の間，要上楼 | 长按“↑二楼”的数字键 | 1 |
| E | 在座敷，要上楼 | 看到“奥の間 ↑”→ 长按它 → 冷却后长按“↑二楼” | 2 |
| F | 在二楼，要下楼 | 长按“↓一楼”的数字键（没有直连时跟着 `↓` 徽标走） | 1–2 |
| G | 在風呂（或台所），要去土蔵 | 长按“⌂土蔵”的数字键 | 1 |
| H | 在玄関，要去土蔵 | 跟着 `⌂` 徽标：台所 → 土蔵（加了建议的那条边时） | 2 |
| I | 在土蔵，要回主屋 | 通道栏里只有“↩ 風呂 / 台所”，长按其一 | 1 |

### T.4 三种视角

三种视角都只在箱女 / 箱人自己的客户端上，不产生任何网络数据。通道栏在三种视角里都显示。

**(1) 箱内视角（现有的，改进）**

- 仍然从容器里往外看，可达的容器隔墙显示剪影。颜色：**黄 = 本房间**，**绿 = 相邻房间**，**蓝 = 另一层楼或土蔵**；准星对准的那个变**红**。“蓝色出口箱”的旧含义没有了。
- **准星对准 + 按 E = 直接转移**，不再需要先点选。`Tab` 轮换目标的功能删掉（Tab 改作地图键）。
- 看不见的目标在屏幕边缘有标记，标记上写**房间名 + 距离**（现在只写距离）。
- 楼上楼下和土蔵的目标不用硬瞄：用通道栏（T.3）。

**(2) 房间视角（“视角转移”）**

- 镜头离开容器，移到某个房间的**俯视机位**（天花板一角往下看整个房间）。只能看**本房间和相邻房间**——也就是下一跳够得着的范围，包括楼梯连着的那层和土蔵。
- 进入方式：短按通道栏的数字键；或者 `W` 移到准星方向上最近的相邻房间，`A` / `D` 在可看的房间之间左右轮换。`S` 回到箱内视角。箱女本来不能走动，WASD 是空着的。
- 在房间视角里，容器同样高亮，准星对准按 E 直接转移。转移完成后镜头回到新容器的箱内视角。
- 镜头在房间之间移动用 0.25 秒的平滑过渡，跨楼层时先抬升再平移，让玩家看得出“这是上楼了”。
- 机位由美术在每个房间放一个 `RoomVantage` 挂点（见 T.10）；没有挂点时退而用“房间中心上方 2.2 m、俯角 40°”。

**(3) 3D 地图（俯瞰整栋房子）**

- `Tab` 开关。镜头拉到房子斜上方，可以用鼠标拖动旋转、滚轮缩放。
- 看到的是一个**简化的房子模型**：每个房间一块地板、半人高的矮墙、门洞留空，没有屋顶和天花板。
- **两层楼上下错开**：二楼整体抬高悬在一楼上方。**土蔵单独摆在后院的位置**，和主屋之间留出空隙。
- **三处特殊连接画成亮线**：两条楼梯是连着上下两层的竖线，后院是连着主屋和土蔵的弧线。玩家一眼就能看出“从哪两个房间能上楼、从哪里能去土蔵”。
- `Z` / `X` / `C`：只看一楼 / 只看二楼 / 全部。
- 每个容器是一个发光的小方块：**红 = 自己所在**，**黄 / 绿 / 蓝 = 现在就能去**（含义同箱内视角），**暗白 = 这一跳去不了**。房间上浮着房间名。
- **左键点现在就能去的容器**：立刻转移。
- **左键点去不了的容器**：不转移，只提示“不相邻”，并把“该先去哪个相邻房间”的那个房间闪一下（和通道栏的方向徽标是同一个信息）。
- **中键点一个可看的房间**：镜头飞到那个房间的房间视角。
- 简化模型由美术生成（T.10，已交付）：放在真房子正下方 300 m，平时整个关着；打开地图的那台客户端把它打开，用一台单独的相机看（关后期）。

### T.6 隐藏信息

- 探索者端收到的东西不变：只有滚动声的粗方位（8 个方向）和三档响度，没有目的地、没有坐标。
- 跨楼层、去土蔵的转移，探索者听到的滚动声和普通转移**是同一类声音**，不因路线不同而不同（见音效方案第 3 节）。
- **房间视角和 3D 地图里显不显示探索者**【待定】。现在箱内视角能看到同房间里走动的探索者；别的房间隔着墙看不到。
  - 【建议】房间视角和 3D 地图里**都不画探索者**（相机剔除探索者所在的层），箱女对别的房间只靠听。否则“视角转移”就变成了全屋监控，这是规则里没有的能力。

### T.8 验收

规则（EditMode）：

1. 同房间任意两个容器互相可达。
2. 相邻房间的任意两个容器互相可达；不相邻的房间不可达。
3. 房间图连通；每个房间至少有一个相邻房间；二楼每个房间到一楼最多 2 跳，一楼每个房间到二楼最多 3 跳；任何房间到土蔵的跳数不超过表里的值（加了建议的边是 4，不加是 5）。
4. 方向徽标：对每个房间，`↑` / `↓` / `⌂` 徽标指向的相邻房间确实让到目标的跳数减 1。
5. 快捷跳的落点：是目标房间里离出发容器最近的可进入容器；那个容器被交互时换下一个最近的；全都进不去时返回“被占用”，不发请求。

联机（现有的多进程冒烟检查里加）：

6. 从台所快捷跳到二楼物置、再跳回来：服务器各收到一次转移请求；探索者端各收到一次滚动声；探索者端始终收不到箱女的位置。
7. 冷却期间的请求被拒绝；进入正在被搜索的容器被拒绝。
8. 把冷却改成 0.5 秒和 10 秒各跑一遍：通道栏的冷却进度和提示音都跟着变，没有写死 3 秒的地方。

手动（T.3 的用例表 A–K 逐条走一遍），另加：

9. 从任意容器出发，只看屏幕提示就能在不查资料的情况下去到土蔵和二楼。

## 3. 阶段 5：开箱死亡与箱人转化、箱人转移

**对应规则**：V1.2 第 2.1、2.2、2.3、2.7 条。

### 5.1 目标

探索者开箱或深搜到有藏匿者的容器 → 被拉入 → 变成箱人 → 用箱女同款的藏匿和普通转移继续玩。

### 5.2 服务器

1. 触发点不变：`MatchRules.AdvanceTo` 在搜索完成时发现容器里有藏匿者就调 `ConvertExplorer`。
2. 把“转化”做成一个统一入口 `ConvertToHakoBito(playerId, containerId, cause)`，后面三种死法都走它：
   - `cause = Opened`：开箱或深搜（本阶段）。
   - `cause = WrongWeakness`：对藏有箱女的容器用错弱点（阶段 6）。
   - `cause = Executed`：猎杀中被处决，容器取最近的有效容器（阶段 8）。
3. 转化的顺序（同一个服务器帧内）：
   1. 结束该探索者的搜索，容器回到关闭状态。
   2. 清空他的全部道具（不掉落、不转交）。手电筒也消失。
   3. 角色改为箱人，位置设为该容器。
   4. 通知相关客户端播死亡演出（现有的 `GrabRpc`：死者本人、12 m 内的探索者、在同一容器里的藏匿者）。
   5. **演出结束后**（时长取 `OccupiedOpening` 的总时长，做成常量 `grabPresentationSeconds`）：销毁他的探索者角色物体，给他生成一个藏匿者角色物体。
4. 藏匿者角色物体：复用 `NetworkHider`，加一个 `role` 字段区分箱女和箱人。
   - 箱女：生成时调 `PlaceHakoOnna`（现状）。
   - 箱人：**不调** `PlaceHakoOnna`，直接读规则核心里已经设好的 `ContainerId`。
   - 可见性同箱女：`CheckObjectVisibility` 只对拥有者可见。
5. 箱人被消灭（阶段 6 才会发生）：角色改为观战者，销毁藏匿者物体，给该客户端一个观战相机。本阶段先把 `Role.Spectator` 的入口留好。
6. 同一个容器里可以同时有箱女和多个箱人（V1.2 第 2.3 条），不做任何互斥。

### 5.3 隐藏信息

- 探索者客户端**收不到**任何箱人的位置：箱人的角色物体对他们不可见，`container` 变量只有拥有者可读。
- 死者的探索者物体被销毁，远处的探索者只会发现“这个人不见了”。不广播“某某死了”。
- 死亡后容器恢复关闭，旁观者看不到里面（现有演出已经是这样）。
- **同阵营之间是否互相知道位置**【待定】：箱女和箱人能不能在箱内视角 / 地图上看到彼此藏在哪个容器。规则里没写。
  - 【建议】互相可见（地图上用另一种颜色标出同伴所在的容器）。他们本来就有不限距离的阵营语音，位置迟早会互相说。

### 5.4 客户端

- 死者：演出（现有）→ 黑屏（现有 `BlackOut`）→ 切到箱内视角，界面换成藏匿者的那一套（模块 T）。背包栏、体力条、手电全部隐藏。
- 箱人的界面比箱女少：**没有能量条、没有猎杀按钮、没有特殊转移**。
- 箱人转移同样播滚动声（服务器已经对所有藏匿者统一处理）。

### 5.5 配置项

| 配置 | 占位值 |
|---|---|
| `grabPresentationSeconds` | 取 `OccupiedOpening` 实际时长 |
| 箱人转移冷却 | 与箱女相同（V1.2 第 2.7 条：规则与箱女的普通转移相同） |

### 5.6 验收

规则（EditMode）：

1. 搜索完成且容器里有箱女 → 探索者变箱人、位于该容器、道具全空、容器关闭。
2. 搜索中途取消 → 不死。
3. 箱女在搜索完成**之前**转移走 → 不死，容器正常打开。
4. 容器里只有箱人（没有箱女）→ 同样致死。
5. 箱人可以普通转移，受冷却限制，不能进入正被交互的容器。
6. 同一容器里箱女 + 两个箱人并存，再来一个探索者开箱，仍然只死他一个。

联机（冒烟检查）：

7. 三个进程（主机箱女、两个探索者）：探索者 A 开到箱女所在的容器 → A 的客户端拥有一个藏匿者物体、原来的探索者物体在所有客户端上都消失；B 的客户端上**不存在**任何藏匿者物体。
8. A 作为箱人转移一次：B 能听到滚动声，B 收不到位置。
9. A 变箱人后，B 去开 A 所在的容器 → B 也变箱人。

### 5.7 美术接口

已有：`HakoOnnaGhost.Spawn(box)`、各类容器的藏匿和扑出姿势、`ContainerVisual.PlayGrab()`（见美术 README“开箱死亡演出”）。本阶段不需要新的美术资产。箱人的外形（死去的探索者）美术还没做，演出里暂时仍然用箱女模型即可。

## 4. 阶段 6：弱点道具与路线一

**对应规则**：V1.2 第 2.8、2.11（路线一）、2.12 条。

### 6.1 本局弱点

- 开局在服务器上从汽油、白木桩、生锈的锁链里**随机一种**作为真弱点，只存在服务器的 `MatchRules` 里。删掉 `LocalSession` 里写死的 `ItemKind.Gasoline`。
- 任何对客户端同步的变量、RPC 参数、日志里都不出现它。调试用命令行参数 `-hakoWeakness <kind>` 可以指定（仅开发版）。

### 6.2 使用方式

- 手持一件弱点道具，准星对准容器（`SearchReach` 以内），按**鼠标左键**使用。不需要先开箱。
- 服务器校验：手持的确实是弱点道具；准星确实对着那个容器（复用 `LookTarget`）；使用者当前没有在搜索。
- 使用时长 `weaknessUseSeconds`【占位：0，即瞬间】。
- 结果直接用 `MatchRules.UseWeakness` 现有的四种返回值：

| 情况 | 结果 |
|---|---|
| 空容器 | 道具消耗，无事发生 |
| 只有箱人 | 道具消耗，容器里的箱人**全部**被消灭（任意一种弱点道具都行）→ 变观战者 |
| 有箱女，弱点正确 | 箱女被击杀 → 路线一达成；同容器里的箱人同样被消灭 |
| 有箱女，弱点错误 | 同容器里的箱人先被消灭；使用者死亡并转化为箱人，位于该容器；箱女不受影响 |

- 错误弱点致死走阶段 5 的 `ConvertToHakoBito(…, WrongWeakness)`，演出和开箱致死相同（设计者已定：用错弱点的死法和开箱一样）。

### 6.3 使用后给探索者的反馈

- 道具从手上消失，播一个“用掉了”的动作和声音（新声音键 `weakness_use`）。
- **是否让使用者知道“里面有箱人被消灭了”**【待定】。规则没写。
  - 【建议】不给区别反馈：空容器和消灭箱人看起来、听起来一样。这样弱点道具不能当探测器用。

### 6.4 路线一结算

- 箱女被击杀 → 所有**存活且未逃离**的探索者共同获胜，箱女阵营失败，对局结束（V1.2 第 2.12 条）。
- 本阶段先做一个最简单的结束状态：服务器进入 `MatchEnded`，所有人停止操作，屏幕中间显示阵营胜负的一行字。正式结算界面【待定】，放到阶段 9。

### 6.5 物品生成（本阶段开始需要）

“物品在容器中的分布与刷新机制”在 V1.2 是【待定】。在设计者定下来之前，先做一个**可替换**的生成器：

- 接口 `IItemPlacement.Place(containers, rng) → (containerIndex, itemKind)[]`。
- 临时实现 `UniformPlacement`【占位】：按配置表里的数量，把物品随机放进互不相同的容器，每个容器最多一件。
- 配置表 `itemCounts`【占位】：汽油 1、白木桩 1、生锈的锁链 1、日记 4、大门钥匙 0（在保险箱里，阶段 9）、Mary 玩偶 1、亡骸 1、老虎钳 1。
- 不刷新：物品被拿走后不再生。

### 6.6 验收

V1.2 要求的五种情况（EditMode，`UseWeakness` 已有部分测试，补齐）：

1. 正确弱点对箱女 → 箱女被击杀，对局结束，存活探索者获胜。
2. 错误弱点对箱女 → 使用者变箱人，箱女还在原容器。
3. 对只有箱人的容器 → 箱人变观战者。
4. 对空容器 → 只消耗道具。
5. 同容器里箱女 + 箱人，用错误弱点 → 箱人被消灭、使用者变箱人、箱女不受影响；这个新转化的箱人**不算**这次使用的目标（现有代码已经这样处理）。

另加：

6. 手上不是弱点道具、准星没对准、正在搜索时使用 → 被拒绝，道具不消耗。
7. 联机：使用者以外的客户端收不到“本局弱点是什么”。

## 5. 阶段 7：能量系统

**对应规则**：V1.2 第 2.5 条，第 2.4 条的特殊转移，第 2.10 条的声音传播。

### 7.1 数据

规则核心里新增 `EnergyRules`（纯 C#）：

- `Current`：当前能量，可消耗，有上限。
- `Total`：累计能量，只增不减。
- 每次获得能量 `x`：`Total += x`；`Current = min(Current + x, cap)`。
- `Paused`：猎杀期间为真，此时四种来源全部不计（V1.2：猎杀期间暂停一切能量获取）。

### 7.2 四种来源

| 来源 | 触发 | 占位数值 |
|---|---|---|
| 时间 | 每秒自动 | `energyPerSecond` = 0.5 |
| 探索者的声音 | 语音：按说话持续时间；动作声：脚步（跑）、开关门、开关容器、丢东西 | 语音 `voicePerSecond` = 1.0；跑步 0.2 / 秒；门 0.5 / 次；容器开或关 1 / 次 |
| 探索者的交互 | 普通搜索完成、深度搜索完成、解锁类操作 | 搜索 2；深搜额外 `deepSearchBonus` = 5；输错保险箱密码 `safeWrongEnergy` = 10（阶段 9 接入） |
| 箱女靠近探索者 | 箱女所在容器与探索者的距离小于 `proximityRange` | `proximityRange` = 6 m；`proximityPerSecond` = 0.5 / 人 |

上限 `energyCap`【占位】= 100。

### 7.3 声音怎么折算

V1.2 第 2.10 条给的低成本做法：**距离衰减 × 固定系数**。

- 距离衰减：`1 − 距离 / hearingRange`，小于 0 取 0。`hearingRange`【占位】= 12 m（猎杀阶段扩大，见阶段 8）。
- 固定系数：同房间 1.0；隔一堵墙（不同房间、同一层）`wallFactor` = 0.5；不同楼层 `floorFactor` = 0.25【占位】。
- “同房间 / 不同房间 / 不同楼层”由 `HouseGraph.RoomAt` 和 `Floor` 判断（模块 T.2）。
- 多个探索者各自独立计算再相加。
- 语音时长由客户端上报（V1.2 明确允许）。语音模块在阶段 10 才接，本阶段用假数据：开发版里按住 `V` 键 = “我在说话”。

### 7.4 同步

- `Current` 和 `Total` 只同步给箱女自己（`NetworkVariableReadPermission.Owner`）。探索者和箱人都收不到。
- 箱女界面：一条当前能量条，条上一道刻线标出特殊转移的门槛。猎杀门槛是按累计能量算的，另用一个小进度环显示“离可以猎杀还差多少”。

### 7.5 特殊转移

- 解锁条件和消耗【占位】：`specialTransferThreshold` = 30（当前能量达到才可用），`specialTransferCost` = 30。
- **具体效果【待定】**——V1.2 明确写了不得自行添加全图瞬移或连续传送。本阶段只做“达到门槛后按钮亮起、按下扣能量”的管线，效果挂在一个空的 `ISpecialTransfer` 接口上，**默认不启用**。
- 给设计者的三个候选【建议，任选或都不要】：
  1. **远跳**：一次可以去两个房间以内的任意容器（普通转移是一个房间）。和新的“一个房间一个房间”最搭。
  2. **无冷却**：这一次转移不进入冷却。
  3. **抢先一步**：可以进入正在被读条（还没打开）的容器。这条会改变“开箱”的博弈，影响最大。
  - 注意第 2.4 条“每次转移必定产生滚动音效”：三个候选都照常出声，没有“无声转移”这个选项。

### 7.6 验收

1. `Current` 和 `Total` 各自独立：消耗只减 `Current`；`Total` 不减。
2. 到达上限后 `Current` 不再涨，`Total` 继续涨。
3. 四种来源各自单独开启时数值正确；两个探索者同时说话时相加。
4. 隔墙和跨楼层的系数生效。
5. `Paused` 时四种来源都不计。
6. 联机：探索者客户端收不到能量数值。

## 6. 阶段 8：猎杀

**对应规则**：V1.2 第 2.6 条、第 2.8 条（对猎杀状态的箱女使用弱点）、第 2.2 条（处决后的转化）。

### 8.1 状态机（服务器，`HuntRules`）

```
未达门槛 ──Total ≥ huntThreshold──▶ 可发动 ──箱女按键──▶ 猎杀中 ──能量耗尽 / 主动回箱──▶ 已结束
```

- `huntThreshold`【占位】= 100（按**累计**能量）。
- 手动发动，**整局只有一次**。发动键 `H`【占位】，按住 1 秒确认，防误触。
- 箱女所在的容器正被打开时也可以发动【默认假设，V1.2 原文】。箱女离开后，那个探索者的搜索照常继续：读条走完时容器里已经没有箱女，正常打开（里面还有箱人的话仍然致死）。
- 发动瞬间：能量来源全部暂停（阶段 7 的 `Paused`）；播 `hunt_start`；箱女离开容器。

### 8.2 猎杀中的箱女

- 箱女变成一个**所有人可见**的角色物体（新预制体 `HakoOnnaHunter`），第一人称，自由移动。
- 移动速度 `huntSpeed`【占位】= 5.5 m/s（探索者跑 5、走 3）。
- 每秒消耗当前能量 `huntDrainPerSecond`【占位】= 4。能量到 0 → 强制回箱。
- 听觉范围扩大：`hearingRange × huntHearingScale`【占位】= 2。
- 不能开门锁门、不能搜索、不能拿东西。门的开合【默认假设】和探索者一样可以推开。

### 8.3 抓捕、救援、处决

- **抓**：箱女在 `grabRange`【占位】= 1.2 m 内对准一名探索者按左键。被抓者进入“被抓”状态：不能移动、不能使用道具、不能搜索；可以转视角、可以说话。
- **处决**：箱女持续抓住同一人 `executeSeconds`【占位】= 6 秒 → 处决。被处决者走 `ConvertToHakoBito(…, Executed)`，落在**离处决地点最近的有效容器**（关闭、未被交互）。
- **救援**：必须用道具（V1.2：不能空手）。对猎杀状态的箱女使用弱点道具：
  - 正确弱点 → 箱女被击杀，路线一达成。
  - 错误弱点 → 道具消耗，箱女被击退 `knockbackDistance`【占位】= 4 m，被抓的队友获救。
- **抓捕人数不设上限**：一次猎杀里可以先后抓多人。
- 以下三点规则里没写清【待定】：
  1. **能当救援道具的是不是只有弱点道具**。【建议】只有弱点道具——和第 2.8 条完全对得上，不用另造规则。
  2. **抓着人的时候箱女能不能移动**。【建议】不能移动，只能转视角（处决的 6 秒是给队友的救援窗口）。
  3. **能不能同时抓两个人**。【建议】一次只能抓一个。

### 8.4 回箱

- **主动回箱**：`returnRange`【占位】= 3 m 内有有效容器（关闭、未被交互）时，对准按 `E` 进入。保留剩余能量。
- **强制回箱**（能量耗尽）：服务器按下面的顺序选容器，把箱女直接送进去：
  1. 关闭、未被交互、**不在任何探索者的视野锥内**的容器里最近的一个。视野锥【占位】：水平 ±50°、距离 15 m、中间没有墙挡住。
  2. 找不到 → 最近的关闭容器。
  3. 仍然找不到（理论上所有容器都开着）→ 最近的任意容器，并强制结束那里的交互。**这一条保证不会卡死。**
- 回箱后：播 `hunt_end`；箱女变回藏匿者；**不能再次离开容器或抓捕**；藏匿、普通转移、特殊转移、开箱致死照旧；能量来源恢复。

### 8.5 箱人在猎杀期间

没有变化：仍然只能藏和普通转移，不能出来（V1.2 第 2.7 条）。

### 8.6 隐藏信息

- 猎杀期间箱女的位置对所有人可见（规则如此）。
- 回箱的**目的地**不告诉探索者：角色物体直接消失。强制回箱特意选视野外的容器，就是为了不暴露。
- 主动回箱时如果有探索者正看着，他能亲眼看到她进了哪个箱子，这是规则允许的。

### 8.7 验收

1. `Total` 没到门槛时发动被拒绝；到了以后可以发动；发动过一次后再发动被拒绝。
2. 猎杀中每秒扣能量，四种来源不计。
3. 能量耗尽 → 强制回箱。对“所有容器都被看着”“所有容器都开着”两种极端情况都能回进去，不卡死（用测试枚举）。
4. 抓住 → 6 秒 → 处决 → 被处决者成为最近有效容器里的箱人。
5. 抓住期间队友用错误弱点 → 被抓者获救、箱女被击退、道具消耗。
6. 用正确弱点 → 箱女被击杀，对局结束。
7. 猎杀结束后不能再出来，其余能力正常。
8. 联机：探索者端在回箱后收不到箱女位置。

### 8.8 需要美术 / 音频提供

- 箱女在容器外的模型和动作：待机、爬行或奔跑、抓人、处决、被击退。现在只有藏匿和扑出的姿势，**这是本阶段最大的外部依赖**。没到位之前用胶囊体占位，不阻塞程序。
- 探索者“被抓”的姿势。
- 猎杀期间的画面处理（美术 README“猎杀画面”一节已有约定）。
- 新声音键：`hunt_grab`、`hunt_execute`、`hunt_knockback`、`hunt_footstep`。

### 8.9 其余待定

- 箱女在猎杀中掉线的处理【待定】（V1.2 第 3 节原有）。阶段 11 一起定。

## 7. 阶段 9：路线二、三、四，计时，路线作废，胜负结算

**对应规则**：V1.2 第 2.9、2.11、2.12 条。

### 9.1 路线二：保险箱与大门

- **保险箱**：一个固定的可交互物体（不是容器，不能藏人）。位置由美术给一个挂点 `Safe`。
- 交互：走到跟前按 `E` 打开密码界面，输入 4 位数字。
  - 正确：保险箱打开，里面是**大门钥匙**（普通物品，占一格）。
  - 错误：播 `safe_wrong`（声音大），箱女获得 `safeWrongEnergy`，保险箱锁定 `safeLockSeconds`【占位】= 20 秒。
  - 可以不靠线索直接猜（V1.2 原文）。
- 密码开局由服务器随机生成，只存在服务器。
- **大门**：现有的院门。手持钥匙对大门按 `E` → 大门**永久打开**，钥匙消耗。之后任何探索者走出大门即逃离（个人结算）。

### 9.2 路线三：亡骸超度

- Mary 玩偶和箱女亡骸是两件普通物品，藏在普通容器里（阶段 6 的物品生成）。
- **超度的最终操作方式【待定】**。
  - 【建议】把两件东西都带到**仏間的佛坛**前，一人手持其中一件、另一件已经放在佛坛上（或同一人先放一件再放一件），然后按住 `E` `riteSeconds`【占位】= 10 秒。期间被打断则重来。完成 → 所有存活探索者共同获胜，对局结束。
  - 理由：房子里本来就有仏間和佛坛，不用新造场所；需要读条，给箱女反应的时间。
- 在设计者确定之前，只做“两件物品可以被拿到”的部分。

### 9.3 路线四：秘密出口

- 深度搜索完成时有概率 `secretExitChance`【占位】= 0.15 发现秘密出口。不保证成功。
- **出口位置的生成方式【待定】**。
  - 【建议】美术在几个房间的地毯下预留 3–4 个候选位置（挂点 `SecretExitCandidate_n`），开局服务器随机选一个。任何一次深搜成功都揭示**这同一个**出口。
- 发现后：地毯掀开（`carpet_reveal`），出口对**所有人**可见，永久如此。
- 出口上有锁链。全图只有一把**老虎钳**。手持老虎钳对锁链按住 `E` `chainCutSeconds`【占位】= 8 秒 → 剪断（`chain_cut`），出口永久打开。老虎钳是否消耗【默认假设：不消耗】。
- 之后任何探索者进入出口即逃离（个人结算）。
- 注意：出口的锁链和弱点道具“生锈的锁链”是两种东西，物品 ID 和外观分开（V1.2 原文）。

### 9.4 日记和线索

- 日记是普通物品，占一格，拿在手上按 `F`【占位键位】阅读，可以边走边看（V1.2 第 2.9 条）。`F` 现在只在容器打开时用作“取出”，平时是空的。
- 每本日记一段文字，是碎片线索，不直接给答案。没有自动推理，没有图鉴。
- 线索内容和本局弱点、保险箱密码的对应：`ClueSet` 开局在服务器上生成，每本日记的文字**在被阅读时**才定向发给阅读者（不提前同步给所有人）。
- **日记的文字内容由谁写、写几套【待定】**。程序先做数据结构：`DiaryTemplate { text, slots }`，槽位可以填“弱点的暗示”“密码的某一位”。先放 4 条占位文本。

### 9.5 逃离

- 逃离的探索者：从地图上移除，进入观战，记为“已逃离”。
- **只要有一人逃离，箱女阵营即判负**；对局继续，剩下的人继续争取个人逃离（V1.2 第 2.12 条）。

### 9.6 计时和结束

- 一局时长 `matchSeconds`【占位】= 1200（20 分钟）。所有人的界面上显示剩余时间。
- 结束条件（V1.2 第 2.12 条，原样实现）：
  1. 路线一或路线三达成 → 存活探索者全体获胜，立即结束。
  2. 场上没有“存活且未逃离”的探索者 → 结束。此前无人逃离 → 箱女阵营获胜。
  3. 时限耗尽 → 结束。此前无人逃离 → 箱女阵营获胜；仍在图内的探索者失败。
  4. 四条路线全部作废 → 箱女阵营立即获胜。
- 同一帧内的结算顺序：先逃离和击杀，再超时。

### 9.7 路线作废检测（【默认假设】，V1.2 原文）

| 路线 | 作废条件 |
|---|---|
| 一 | 世界上已不存在正确弱点道具 |
| 二 | 大门尚未打开，且钥匙已消失 |
| 三 | 超度尚未完成，且 Mary 玩偶或亡骸已消失 |
| 四 | 锁链尚未剪断，且老虎钳已消失 |

“消失”只有一种途径：携带者死亡（道具随死亡清空）。每次有人死亡后检查一次。

### 9.8 结算界面【待定】

先做最简版：阵营胜负一行字 + 每个玩家一行（角色、是否逃离、是否存活）。

### 9.9 验收

1. 每条路线可以单独通关（三个 EditMode 流程测试 + 手动各走一遍）。
2. 第一个人逃离后：箱女阵营被标记失败，对局不结束，第二个人还能逃。
3. 输错密码：锁定、给能量、有声音。
4. 四条路线逐一作废后箱女阵营立即获胜；只作废三条时不结束。
5. 同一帧里“最后一人逃离”和“超时”同时发生 → 算逃离。
6. 密码、出口位置、日记内容在使用前不出现在任何探索者客户端。

### 9.10 需要美术提供

保险箱模型和挂点、大门的开合（已有门扇）、佛坛的交互挂点、3–4 个秘密出口候选位置和地毯掀开的表现、锁链、Mary 玩偶、亡骸、老虎钳、钥匙、日记的模型和图标。美术 README“秘密出口”一节已有部分约定。

## 9. 阶段 11：掉线与重连

**对应规则**：V1.2 第 2.4 条（箱女掉线）、第 3 节的待定项。

### 11.1 已确认的部分

- 箱女掉线：**留在原容器**，探索者打开该容器仍然死亡。允许重连。
- 实现：连接时带一个本局内不变的玩家标识；服务器保留 `MatchRules.Player` 和它的容器位置，不因断线而移除；重连时把藏匿者物体重新交给这个客户端，能量、冷却、是否已猎杀过全部沿用。

### 11.2 待定的部分（V1.2 第 3 节原有，这里逐条给建议）

| 问题 | 【建议】 |
|---|---|
| 探索者掉线 | 身体留在原地 `disconnectGraceSeconds` = 60 秒，期间可以被抓、被处决。超时以后有两种做法，后果差别很大，**要设计者选**：(a) 直接移出对局，身上的道具消失（可能让某条路线作废）；(b) 按死亡处理，变成一个没人操作的箱人留在最近的容器里 |
| 探索者重连 | 宽限期内回到原来的身体和背包 |
| 中途加入 | 不允许。对局开始后新连接只能观战 |
| 箱女在猎杀中掉线 | 立即按“能量耗尽”处理：强制回箱，猎杀次数算用掉 |
| 箱人掉线 | 留在原容器（和箱女一致） |

### 11.3 验收

V1.2 要求：箱女掉线后留在原容器且开箱仍致死。另加：箱女重连后能量、冷却、猎杀次数不变；重连前后探索者端都收不到她的位置。
